# Claude Plan Executor — Requirements Spec

A CLI/TUI tool that automates the planbot → next-phase → summarise-plan loop, queueing work across repos and chewing through it while you sleep — pausing automatically when Claude Code session limits are hit and resuming when the window reopens.

Working name: **Claude Plan Executor** (`cpe`).

---

## 1. Goals

- Drive an end-to-end planbot workflow (plan → execute phases → summarise → PR) with minimal human intervention
- Maximise use of 5-hour session limit windows, including overnight
- Support a queue of plans across multiple repos, processed sequentially
- Each phase runs in a fresh Claude Code session to avoid context drift
- Single distributable binary, installed globally, callable from any repo

## 2. Non-goals (initial scope)

- Parallel/concurrent phase execution (one Claude Code process at a time)
- Background daemon — tool runs in the foreground with TUI visible
- Cross-platform beyond Ubuntu/WSL (Linux primary; mac/win later if easy)
- Replacing planbot's interactive planning intelligence (it still drives that step)

## 3. Tech stack

| Concern | Choice |
|---|---|
| Language | TypeScript |
| Runtime | Bun |
| Distribution | `bun build --compile` → single binary, installed globally |
| TUI | Ink (React-for-terminal), works with Bun |
| Git | `simple-git` or shelling out to `git` |
| VCS APIs | Shell out to `gh` for GitHub, `tea` (or REST) for Gitea |
| Storage | JSON files under `~/.config/claude-plan-executor/` and `~/.local/state/claude-plan-executor/` |
| Prompts | Embedded in the binary (see §4.1) — not dependent on user's skills directory |

## 4. Core concepts

- **Plan** — a `docs/<folder>/` directory containing `README.md`, `PROGRESS.md`, and `PHASE_NN.{md,prompt.md}` files (planbot output)
- **Phase** — a single `PHASE_NN.prompt.md` to be executed by a fresh Claude Code session, producing one commit
- **Run** — a queued plan being executed, tracked from queued → executing → complete/failed/paused
- **Queue** — ordered list of runs, processed FIFO
- **Session** — one `claude -p` invocation, scoped to a single phase

### 4.1 Embedded prompts

The tool ships its own versions of the prompts it needs, so it doesn't depend on the user having any particular skills installed in their Claude Code config. The prompts live in the repo at `src/prompts/` and are bundled into the binary at build time.

| Prompt | Purpose | Delivery |
|---|---|---|
| `planbot.md` | System prompt for the interactive planning session. Adapted from the planbot skill but adjusted for this tool's conventions: **single feature branch with one commit per phase**, no phase branches, no per-phase PRs. Each generated `PHASE_NN.prompt.md` must instruct Claude to (a) commit at the end of the phase with a conventional message, (b) update `PROGRESS.md` for human readability (cosmetic — see §4.2), and (c) emit a final JSON message matching the phase result schema (§7.3.1) before exiting. | Written to a temp file; `claude` is launched with this as the initial user message, then the session continues interactively |
| `summarise.md` | System prompt for the non-interactive summarise step. Produces `docs/<folder>.md` and deletes `docs/<folder>/`. Takes the folder name as a parameter (injected by the tool). | Piped to `claude -p` as the initial message |

The `next-phase` skill has no embedded equivalent — its logic *is* the tool (read `meta.json` to find the next pending phase, spawn `claude -p` with that phase's prompt file).

**Versioning**: plans already generated by an older version of the tool retain their phase prompts; updates to the embedded `planbot.md` only affect new plans. The embedded `summarise.md` is re-read on every run, so improvements to summarisation apply immediately.

### 4.2 State ownership

The tool's own JSON files (`meta.json` per run, see §5) are the **authoritative source of phase state** — which phase is next, which are complete, retry counts, commit SHAs, timestamps. The tool never parses `PROGRESS.md` to make decisions, because LLM-generated markdown table formatting is too inconsistent to rely on.

`PROGRESS.md` remains in the repo as a human-readable artifact. The embedded `planbot.md` still instructs Claude to update it as each phase completes — that's useful for anyone browsing the repo — but the tool treats it as cosmetic. If `meta.json` and `PROGRESS.md` disagree, `meta.json` wins.

The set of phases for a plan is determined at queue time by enumerating `PHASE_*.prompt.md` files in `docs/<folder>/` on the filesystem (not by reading PROGRESS.md).

### 4.3 Worktree model

Every run executes in its **own `git worktree`**, not in the user's primary clone of the repo. This means:

- Multiple runs against the same repo can coexist on disk, each on its own branch, without waiting for PRs to merge first
- The user's primary checkout is never touched — they can keep working on `main` (or anything else) while runs process
- Failed runs leave a worktree on disk for inspection; clean recovery via `cpe clean`

Worktrees live at `~/.local/state/claude-plan-executor/worktrees/<run-id>/` and are created from the primary clone via `git worktree add`. The primary clone is identified at `cpe plan` time via `git rev-parse --show-toplevel`.

**Branch naming**: at `cpe plan` time the final plan slug isn't known yet (planbot picks it). The worktree starts on a temporary branch `cpe/planning-<timestamp>`. Once planning completes and a `docs/<folder>/` is produced, the tool renames the branch (`git branch -m`) and the worktree directory (`git worktree move`) to match `feature/<folder>`. If the user bails on planning (no folder produced), the worktree is removed and the temp branch deleted.

## 5. Storage layout

```
~/.config/claude-plan-executor/
  config.json          # global settings (defaults, VCS tokens, bootstrap hooks, etc.)

~/.local/state/claude-plan-executor/
  queue.json           # the active queue
  runs/
    <run-id>/
      meta.json        # authoritative run + phase state (see below)
      logs/
        phase-01.log   # captured session output
        phase-02.log
        ...
  worktrees/
    <run-id>/          # git worktree for this run (see §4.3)
```

Shape of `meta.json` (illustrative):

```json
{

  "primary_repo_path": "/home/richard/code/meatbot",
  "worktree_path": "/home/richard/.local/state/claude-plan-executor/worktrees/01H.../",
  "plan_folder": "001-add-tests",
  "feature_branch": "feature/001-add-tests",
  "target_branch": "main",
  "remote": { "host": "github.com", "owner": "...", "repo": "..." },
  "status": "executing",
  "total_cost_usd": 0.1875,
  "phases": [
    {
      "number": 1,
      "prompt_file": "PHASE_01.prompt.md",
      "status": "complete",
      "retry_count": 0,
      "commit_sha": "abc1234",
      "started_at": "...",
      "completed_at": "...",
      "session_id": "17b556b6-...",
      "cost_usd": 0.0376,
      "tokens": { "input": 4, "output": 95, "cache_read": 33037, "cache_creation": 6854 },
      "summary": "Added unit test for login function",
      "notes_for_next_phase": ""
    },
    { "number": 2, "prompt_file": "PHASE_02.prompt.md", "status": "executing",  "retry_count": 0, "started_at": "..." },
    { "number": 3, "prompt_file": "PHASE_03.prompt.md", "status": "pending" }

```

The per-phase `session_id`, `cost_usd`, `tokens`, `summary`, and `notes_for_next_phase` are pulled from the envelope (§7.3 step 6) on phase completion. `total_cost_usd` at the run level is the rolling sum across completed phases.

`primary_repo_path` is the user's original clone (for grouping/display). `worktree_path` is where execution actually happens.

## 6. CLI surface

| Command | Purpose |
|---|---|
| `cpe plan [details...]` | Launch interactive `claude` in current repo, seeded with the embedded planbot prompt plus the user's plan details. If no details given, prompt the user for them via multiline input first. Watches `docs/` for a new plan folder; on detection, offers to queue it |
| `cpe queue [folder]` | Add a plan to the queue. If no folder given, list folders under `docs/` and let user pick |
| `cpe start` | Start the TUI / queue processor |
| `cpe status` | Print queue status (non-TUI, for scripting) |
| `cpe list` | List runs in queue |
| `cpe remove <run-id>` | Remove a run from the queue |
| `cpe pause` / `cpe resume` | Pause/resume queue processing |
| `cpe clean` | Remove worktrees for completed/merged runs (and their state). Prompts for confirmation per worktree, or `--all` to sweep |

## 7. Workflow detail

### 7.1 Plan creation (`cpe plan [details...]`)

1. User runs `cpe plan <details>` inside a repo — e.g. `cpe plan add tests for the user service`
2. If no details were supplied on the command line, CLI opens a multiline input (terminate with EOF / `Ctrl+D`) and captures them
3. CLI identifies the primary repo via `git rev-parse --show-toplevel`
4. CLI allocates a run-id and creates a worktree: `git worktree add ~/.local/state/claude-plan-executor/worktrees/<run-id> -b cpe/planning-<ts> main` (target branch is configurable, defaults to `main`)
5. CLI optionally runs the repo's configured **bootstrap hook** if defined in `cpe.config.json` at the repo root (e.g. `npm install`) — needed so the planning session can see a working tree
6. CLI assembles the kickoff message: the embedded `planbot.md` prompt, followed by a separator, followed by the user's plan details (treated as the initial feature request)
7. CLI writes the assembled message to a temp file and spawns Claude as: `claude < temp_file` with `cwd` set to the worktree. **Verified mechanism (probe-claude-cli, 2026-05-17)**: this causes Claude to read the file as the initial user message, generate its first response, and then hand the TUI to the user for follow-up. `--append-system-prompt` and `--system-prompt` only load context — they don't auto-execute the message, which is why stdin redirection is the right tool here.
8. User completes the planning conversation interactively, then exits Claude
9. On Claude exit, CLI checks the worktree's `docs/` for a newly-created folder containing `PROGRESS.md`:
   - **None found** → user bailed: `git worktree remove --force <path>` followed by `git branch -D cpe/planning-<ts>` (the `worktree remove` does not delete the branch — verified by probe-git-worktree.sh). No run recorded.
   - **Found** → rename the branch (`git branch -m cpe/planning-<ts> feature/<folder>`), move the worktree directory to match (`git worktree move <new-path>`), and prompt: "Queue this plan now? [Y/n]"
10. If queued → invoke queue logic. The planning docs are committed as the first commit on the feature branch (`docs: plan <folder>`)

### 7.2 Queueing (`cpe queue`)

When called from `cpe plan`, the worktree, feature branch, and docs commit already exist. When called standalone (`cpe queue [folder]`, e.g. on a plan you've authored manually), the tool first creates the worktree the same way `cpe plan` would — checking out from `main` and applying the existing `docs/<folder>/` content onto it as a commit.

Pre-checks:
- `PROGRESS.md` exists in the plan folder (presence-checked only, not parsed)
- At least one `PHASE_*.prompt.md` file exists
- Worktree path is available (no collision)

Enumerate phases by globbing `PHASE_*.prompt.md` in the worktree's plan folder, sorted numerically, and write one entry per file into `meta.json.phases` with status `pending`. This is the only point at which the filesystem is the source of truth for the phase list; from here on, `meta.json` is.

Record in `meta.json`:
- Run-id, primary repo path, worktree path
- Plan folder name, feature branch, target branch
- Detected remote (GitHub/Gitea/other)
- Phase list (as above)

### 7.3 Phase execution (per phase, per run)

The next phase to run is determined by scanning `meta.json.phases` for the first entry with status `pending` (or `executing` if resuming after a crash). PROGRESS.md is not consulted.

1. **Limit check** — if rate-limited, set run to `paused-limit`, poll until window resets
2. **Update state** — set the phase entry status to `executing`, write `meta.json`
3. **Capture HEAD** — `git rev-parse HEAD`, stored on the phase entry
4. **Spawn session** — `claude -p --output-format=json --json-schema <phase-result-schema> < PHASE_NN.prompt.md` with **`cwd` = `worktree_path`**, stream stdout to TUI pane and `phase-NN.log`. **Both flags are mandatory together**: probe-claude-json-schema (2026-05-17) confirmed `--json-schema` alone with the default text output silently suppresses the structured output. The runner must error out at startup if asked to run without both. Output is a single JSON envelope on stdout (no chunking, since not using `--include-partial-messages`). Also worth evaluating during build: `--max-budget-usd` as a per-phase safety cap, `--bare` to suppress user-level CLAUDE.md/skills
5. **Wait for exit**
6. **Parse the JSON envelope** from stdout. Key fields read by the runner:
   - `is_error` (bool) — primary success/failure signal
   - `api_error_status` (int|null) — HTTP status if `is_error`. `429` ⇒ rate-limit hit, treat as §8 limit case (no retry consumed)
   - `terminal_reason` (str) — e.g. `"completed"` for clean exit
   - `stop_reason` (str) — Claude's reason for ending the conversation
   - `structured_output` (object) — the schema-validated phase result (§7.3.1)
   - `usage.{input_tokens, output_tokens, ...}` — store on the phase entry for metrics
   - `total_cost_usd` (float) — store on the phase entry for cost accounting
   - `session_id` (str) — UUID pointing to the corresponding jsonl file in `~/.claude/projects/`
   - `permission_denials` (array) — log if non-empty; useful diagnostic when a phase mysteriously fails
7. **Decide phase outcome** using the envelope:
   - `is_error: true, api_error_status: 429` → §8 limit case (pause run, don't count retry)
   - `is_error: true` (other) → phase failure, retry/fail per usual rules
   - `is_error: false` and `structured_output.completed: true` and `structured_output.committed: true` → continue to step 8
   - Anything else (envelope unparseable, missing required schema fields, contradictions) → phase failure
8. **Cross-check HEAD** — `git rev-parse HEAD`:
   - If `structured_output.committed: true` AND HEAD changed → success. Record new HEAD as `commit_sha` in `meta.json`
   - If `structured_output.committed: true` but HEAD is unchanged → failure (Claude misreported), log the discrepancy
9. **Mark complete in `meta.json`** — set `completed_at`, status `complete`, store `summary`, `notes_for_next_phase`, `cost_usd`, `tokens`, `session_id` from the envelope. PROGRESS.md updates by Claude remain cosmetic — see §4.2
10. **Failure handling**:
    - Retry up to `max_retries` (default 1, configurable per-run and globally), incrementing `retry_count`
    - On retry exhaustion: mark phase `failed`, pause this run, move to next queued run
    - Limit-hit (429) does **not** count toward retries — it triggers the §8 wait

### 7.3.1 Phase result schema

Passed to every phase invocation via `--json-schema`. The validated object appears as the `structured_output` key of the response envelope (§7.3 step 6), **not** the top-level `result` field (`result` is for unstructured prose, which is empty when a schema is in use). Embedded in the binary alongside the prompts (§4.1).

```json
{
  "type": "object",
  "required": ["completed", "committed", "summary"],
  "properties": {
    "completed": {
      "type": "boolean",
      "description": "True if the phase's stated goal was fully achieved. False if any part was skipped, deferred, or blocked."
    },
    "committed": {
      "type": "boolean",
      "description": "True if a git commit was made as part of this phase."
    },
    "commit_message": {
      "type": ["string", "null"],
      "description": "The commit message used, or null if no commit was made."
    },
    "summary": {
      "type": "string",
      "description": "One-to-two sentence human-readable description of what changed.",
      "maxLength": 500
    },
    "blockers": {
      "type": "array",
      "items": { "type": "string" },
      "description": "Anything that prevented full completion. Empty if completed cleanly."
    },
    "notes_for_next_phase": {
      "type": "string",
      "description": "Information the next phase should be aware of. Empty if not applicable."
    }
  }
}
```

The embedded `planbot.md` (§4.1) must instruct generated phase prompts to end with: *"Your final message in this conversation must be a JSON object matching the schema you've been given. Do all your work using tools first, then emit only the JSON as your closing message."*

### 7.4 Finalisation (after final phase)

All commands below run inside the worktree.

1. Spawn headless `claude -p` with the embedded `summarise.md` prompt (folder name injected)
2. Verify `docs/<folder>.md` was created and `docs/<folder>/` was deleted
3. CLI commits the summary (single commit, message: `docs: summarise <folder>`)
4. Push feature branch to remote (`git push -u origin <feature_branch>`)
5. Detect remote host:
   - `github.com` → `gh pr create --base <target> --fill`
   - Self-hosted Gitea (detected via remote URL match against configured Gitea host) → `tea pr create` or REST API
6. Capture PR URL, mark run `complete`, surface URL in TUI
7. **Worktree is retained** for inspection. It will be removed on next `cpe clean` (or auto-cleaned in a future iteration once we can poll the PR for merged status)

## 8. Limit detection

Three signals available, in order of preference. Since the phase runner uses `claude -p --output-format=json --json-schema ...` (§7.3 step 4), the envelope is the natural primary signal.

### 8.1 Envelope-based (primary)

When using `--output-format=json`, the envelope contains:
- `is_error: bool`
- `api_error_status: int | null` — HTTP status code

Logic:
- `is_error: true` AND `api_error_status: 429` → rate-limit hit
- `is_error: true` AND `api_error_status: 500/502/503` → transient API error, retry quickly (separate from session-limit pause)
- `is_error: true` AND `api_error_status: 400/401/403` → genuine error, fail the phase, don't pause
- `is_error: false` → success path

**Not yet confirmed**: that a rate-limit produces a JSON envelope at all when both flags are set. Probe-claude-json-schema ran below the limit, so we only saw the success case. Next time a limit is hit, the runner should be tested with `--output-format=json --json-schema ...` to confirm `is_error: true, api_error_status: 429` populates as expected (rather than falling back to the §8.2 stdout pattern).

### 8.2 Stdout pattern (fallback)

Captured from probe-active-limit (2026-05-17) using bare `claude -p`:

- **Exit code**: `1`
- **stdout** (single line): `You've hit your limit · resets <reset_time>`
- **stderr**: empty
- Returns in ~1s

Anchor regex on the distinctive middle-dot separator `·` (U+00B7) and the literal "resets":

```regex
^You've hit your limit · resets (?P<reset>.+?)$
```

The capture group is a human-readable reset time like `4pm (Europe/London)` — a time-of-day in 12-hour format followed by an IANA timezone name in parentheses. **No date** is included.

**Reset-time parsing algorithm:**
1. Split the captured string into the time portion and the parenthesised timezone
2. Parse the time as `%-I%p` (e.g. `4pm` → hour 16)
3. Get `now` in the named timezone
4. Build `reset_dt` = today at `reset_hour`, in the named timezone
5. If `reset_dt <= now` (already passed today), add 24 hours
6. `wait_until = reset_dt`

If the regex matches the limit line but the reset string fails to parse, fall back to polling every 5 minutes.

### 8.3 jsonl confirmation (auxiliary)

When a rate-limit error occurs during a session, three fields appear on the relevant message entry in `~/.claude/projects/<encoded-cwd>/<uuid>.jsonl`:

```
error: str           // observed: 10 chars, likely "rate_limit"
isApiErrorMessage: bool
apiErrorStatus: int  // HTTP status code (e.g. 429)
```

Uses:
- **Confirmation**: after marking a run `paused-limit`, scan recent jsonl entries across all projects for `isApiErrorMessage: true` with a timestamp inside the suspected window. Useful as a sanity check
- **Per-account token accounting (v2)**: sum `.message.usage.{input_tokens, output_tokens}` across all jsonl files within the current 5-hour window for predictive "% of window used" display. Aggregate across **all** projects, not just the current run — the limit is per account

### 8.4 Working order during build

1. Implement envelope-based detection (§8.1) — the runner already needs the envelope for §7.3 anyway
2. Confirm 429-via-envelope behaviour the next time a limit is naturally hit during testing
3. Implement §8.2 regex as a defensive fallback in case the envelope doesn't carry rate-limit info in `-p --output-format=json` mode (also needed for any non-envelope `claude` invocations)
4. Optional v2: jsonl-driven predictive display in the TUI (§8.3 second use)

When a limit is detected:
- Mark current run `paused-limit`
- Sleep until parsed reset time (envelope may include this; if not, fall back to §8.2 parsing or 5-min polling)
- Resume the same phase from scratch (fresh session) when the window opens

Layout (Ink):

```
│ Queue (3 runs)                  │  Active: meatbot phase 4/14  │
│ ▶ meatbot          phase 4/14   │  ┌─ Session output ────────┐ │

│                                 │  │                         │ │
│                                 │  └─────────────────────────┘ │

│ Limit window: resets in 2h 14m  │  q quit  p pause  r remove  │

```

Key bindings:
- `q` — quit (warn if a session is active; require confirmation)
- `p` — pause/resume queue
- `r` — remove highlighted run
- Arrow keys to select run, `Enter` to view full log

## 10. Resilience

- **Tool crash / forced exit mid-phase**: on next `cpe start`, detect run with `executing` status; ask user: resume phase, mark failed, or skip
- **Graceful exit warning**: if `q` pressed while a session is active, confirm before killing
- **Phase-prompt commit failure**: HEAD-unchanged check catches Claude forgetting to commit; counts as a phase failure → retry/fail per usual rules
- **Disk persistence**: queue and run state written after every state change, not just on shutdown
- **Worktree reconciliation**: on startup, cross-reference `git worktree list` for each primary repo against `meta.json` records; warn on mismatches (worktree deleted out-of-band, or recorded worktree no longer exists)

- ~~Worktree rename + move mechanics~~ → resolved: works cleanly, but temp branch must be deleted explicitly
- ~~Where Claude Code stores session data~~ → resolved: `~/.claude/projects/<encoded-cwd>/<uuid>.jsonl`
- ~~`claude -p` exit code on limit-hit~~ → resolved: exit 1, distinctive stdout line, see §8.2

**Still open:**
- Confirm that a 429 rate-limit hit while using `--output-format=json --json-schema ...` returns a JSON envelope with `is_error: true, api_error_status: 429` (vs. falling back to the §8.2 stdout format). Test next time a limit is naturally hit. The §8.2 regex is implemented either way as a fallback
- Whether `--bare` is the right default for phase execution — it skips CLAUDE.md auto-discovery, hooks, plugins, etc. The phase prompt should be self-contained, so `--bare` makes runs more reproducible. But the user's CLAUDE.md might contain useful project context. Default off, configurable on
- Whether `--max-budget-usd` is worth setting as a per-phase safety cap (we now know `total_cost_usd` is in the envelope, so we can also enforce caps post-hoc)
- Bootstrap hook design: `cpe.config.json` at repo root with a `bootstrap` command string? Per-phase bootstrap (rare) vs once-per-worktree (default)? Skipped silently if absent
- Auto-cleanup of worktrees: poll PR status (merged/closed) and remove on merge, vs manual `cpe clean` only. Start manual, add polling later if useful

### 11.1 Claude Code features deliberately not used

Surfaced during probes; documented here so we don't revisit:

- **`claude --worktree` / `-w`**: creates a worktree *per session*, not what we want — our worktrees span many sessions across the whole plan
- **`claude --tmux`**: creates a tmux session; not appropriate inside our own TUI
- **`claude --resume` / `--continue` / `--session-id`**: by design, each phase is a *fresh* session for context-drift reasons. We don't want session continuity
- **`claude --from-pr`**: unrelated to our workflow


## 12. Build phases (preview, not committed)

A natural planbot split looks like:

1. Project skeleton: Bun + TS + Ink + single-binary build pipeline, with `src/prompts/` bundled into the binary
2. Embedded prompts: write the tool's `planbot.md` (adapted for single-branch / commit-per-phase) and `summarise.md`
3. Storage layer: config, queue, run-state persistence
4. Worktree management: create, rename/move, remove, reconcile against `git worktree list`
5. CLI command parsing + non-TUI commands (`queue`, `list`, `remove`, `status`, `clean`)
6. Claude Code session runner (spawn, stream, exit handling)
7. Phase execution loop with HEAD-diff commit verification, running in the worktree
8. Limit detection (stdout parsing first)
9. TUI shell with Ink (queue + session output panes)
10. Finalisation: summarise step (using embedded prompt) + push from worktree
11. VCS detection + PR creation (GitHub + Gitea)
12. `cpe plan` flow: worktree creation, embedded planbot kickoff, branch rename on success, cleanup on bail
13. Bootstrap hooks (`cpe.config.json` per repo)
14. Resilience: resume-on-restart, graceful exit, retries, worktree reconciliation
15. Limit-detection v2 spike (Claude-Code-Usage-Monitor approach)
16. Polish, docs, install script
