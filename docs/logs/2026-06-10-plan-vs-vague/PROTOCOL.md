# Experiment: frontier-planned phases vs vague prompt on a local 12b

**Pre-registered protocol — written and committed BEFORE any run executes.**

## Hypothesis

Detailed, scoped phase prompts generated by a frontier model (planbot on
claude-code + Anthropic) let a small local model (gemma4-cpe:12b) complete a
mid-size feature on a real codebase that it fails (or half-delivers) when given
the raw feature request directly. Basis: in the 2026-06-10 matrices, every
model-level failure was a *discovery/decision* failure under ambiguity, never an
*editing* failure — and phase prompts exist to remove discovery and decisions.

## Task (deliberately at/above the 12b's comfort zone)

Self-update support for cpe, on the real cpe codebase:

- explicit version check (current + latest available) and explicit update
  (download + install)
- automatic background check and install during normal use
- when an update lands while the TUI is open, prompt the user to restart

Ground truth that exists in the repo: `CPE_VERSION` (build-time `--define`,
`'dev'` locally), GitHub Releases with 4 platform binaries,
`scripts/install.sh` (downloads `latest` asset to `~/.local/bin/cpe`),
`docs/install-and-release.md`, TUI conventions in `docs/DESIGN.md`.

## Design

| | Arm A (control) | Arm B (planned) |
|---|---|---|
| Input | the vague prompt below, verbatim | planbot plan (claude-code + Anthropic), phases executed sequentially |
| Executor | pi AND aider (separate runs) | pi AND aider (separate runs of the same plan) |
| Model / provider | gemma4-cpe:12b / homelab-litellm | same |
| Isolation | worktree of a remote-less clone | same |

The plan in Arm B is generated **once**; the planning baseline is duplicated so
both executors run the identical plan. The planning session may NOT see this
protocol or the checklist (requirements come from the user answering planbot's
questions in their own words).

## Arm A prompt (verbatim, both executors)

> cpe has no way to keep itself up to date. Can you add version checking and
> updating? I want to be able to check my version and update explicitly, but
> ideally it also just checks by itself and installs new versions when they come
> out — and if it updated underneath a running session, let me know so I can
> restart it. We ship binaries on GitHub releases.

This is also the kickoff text for the Arm B planning session (planbot then asks
its clarifying questions).

## Acceptance checklist (graded per run, pass/fail each)

1. A command reports the **running version** and the **latest available** release.
2. Latest-release lookup targets the repo's real mechanism (GitHub Releases API).
3. Explicit update **downloads the correct platform asset** and replaces the
   installed binary, reporting what it did.
4. **Already-up-to-date** is a graceful no-op (no re-download).
5. **`dev` builds** are handled sanely (no crash, no bogus "update" from `dev`).
6. **Auto-check** runs during normal use without blocking startup.
7. **Auto-install** happens without user action when a newer release exists.
8. A **running TUI shows a restart prompt/notice** after an in-session update.
9. **Network failure / API errors never break normal operation** (offline-safe,
   no unhandled rejections).
10. **Unit tests** cover version comparison / update decision; existing
    build + lint + tests still pass.
11. Work is **committed** (Arm B: one commit per phase; phases complete).

Secondary metrics: wall time, litellm tokens (in/out), requests, phases
completed (B), notes flow between phases (B). Bonus yardstick: compare designs
against the parked frontier-model attempt at the smaller version of this feature
(`~/.local/state/cpe/worktrees/01KSN7WWHJ0745DA4966QSF2F9`, May 27).

## Procedure

1. Baselines: `git clone -b feature/harness-bench <repo> ~/Code/cpe-exp/armA`
   (remote removed); same for `armB-plan`.
2. Queue Arm A from `armA`:
   `cpe prompt "<prompt above>" --harness pi --provider homelab-litellm --model gemma4-cpe:12b`
   then the same with `--harness aider`. Run with `cpe start`.
3. Arm B planning (user, interactive): from `armB-plan`,
   `cpe plan --provider anthropic "<prompt above>"` — answer planbot's questions
   honestly; decline the queue offer at the end.
4. Duplicate `armB-plan` → `armB-pi`, `armB-aider`; queue each:
   `cpe queue <plan-folder> --harness <pi|aider> --provider homelab-litellm --model gemma4-cpe:12b`;
   run with `cpe start`.
5. Grade all four runs against the checklist from diffs + running the code in
   the worktrees. Record per-criterion pass/fail before reading any tokens/time
   metrics (grade blind to cost).

## Outcome interpretation (committed to in advance)

- B ≫ A on criteria met → hypothesis supported: frontier planning + local
  execution is the homelab pattern.
- B ≈ A, both high → 12b is stronger than assumed; planning buys structure
  (commits/phases) not capability.
- B ≈ A, both low → the task exceeds 12b regardless; re-run Arm B at 26b/31b to
  find the floor.
- A > B → planning overhead actively hurts at this size (instruction-volume
  sensitivity); investigate the phase prompts.
