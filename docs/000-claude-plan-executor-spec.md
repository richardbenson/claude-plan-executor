# Claude Plan Executor — Requirements Spec

A CLI/TUI tool that automates the planbot → next-phase → summarise-plan loop, queueing work across repos and chewing through it while you sleep — pausing automatically when Claude Code session limits are hit and resuming when the window reopens.

Working name: **Claude Plan Executor** (`cpe`).

**Companion documents** (in this repo at `docs/`):
- **`DESIGN.md`** — source-of-truth TUI design (layout, palette, state mapping, keybinds). This spec defers to it for everything visual.
- **`tui-design.html`** — visual reference, open in a browser to see DESIGN.md realised.

---

## 1. Goals

- Drive an end-to-end planbot workflow (plan → execute phases → summarise → PR) with minimal human intervention
- Maximise use of 5-hour session limit windows, including overnight
- Support a queue of plans across multiple repos, processed sequentially
- Each phase runs in a fresh Claude Code session to avoid context drift
- Single distributable binary, installed globally, callable from any repo

## 2. Non-goals (initial scope)

- Parallel/concurrent phase execution (one Claude Code process at a time)
- Background daemon — tool runs in the foreground with TUI visible
- Cross-platform beyond Ubuntu/WSL (Linux primary; mac/win later if easy)
- Replacing planbot's interactive planning intelligence (it still drives that step)

## 3. Tech stack

| Concern | Choice |
|---|---|
| Language | TypeScript |
| Runtime | Bun |
| Distribution | `bun build --compile` → single binary, installed globally |
| TUI | Ink (React-for-terminal), works with Bun |
| Git | `simple-git` or shelling out to `git` |
| VCS APIs | Shell out to `gh` for GitHub, `tea` (or REST) for Gitea |
| Storage | JSON files under `~/.config/cpe/` and `~/.local/state/cpe/` |
| Prompts | Embedded in the binary (see §4.1) — not dependent on user's skills directory |

## 4. Core concepts

- **Plan** — a `docs/<folder>/` directory containing `README.md`, `PROGRESS.md`, and `PHASE_NN.prompt.md` files (planbot output)
- **Phase** — a single `PHASE_NN.prompt.md` to be executed by a fresh Claude Code session, producing one commit
- **Run** — a queued plan being executed; status transitions through the state taxonomy in §5.1
- **Queue** — ordered list of runs, processed FIFO
- **Session** — one `claude -p` invocation, scoped to a single phase

### 4.1 Embedded prompts

The tool ships its own versions of the prompts it needs, so it doesn't depend on the user having any particular skills installed in their Claude Code config. The prompts live in the repo at `src/prompts/` and are bundled into the binary at build time.

| Prompt | Purpose | Delivery |
|---|---|---|
| `planbot.md` | System prompt for the interactive planning session. Adapted from the planbot skill but adjusted for this tool's conventions: **single feature branch with one commit per phase**, no phase branches, no per-phase PRs. Each generated `PHASE_NN.prompt.md` must instruct Claude to (a) commit at the end of the phase with a conventional message, (b) update `PROGRESS.md` for human readability (cosmetic — see §4.2), (c) emit a final JSON message matching the phase result schema (§7.3.1) before exiting, and (d) be **idempotency-aware** — check working tree state before each significant action, so the phase is safe to resume after a rate-limit interruption (§7.3.2). | Written to a temp file; `claude` is launched with this as the initial user message, then the session continues interactively |
| `summarise.md` | System prompt for the non-interactive summarise step. Produces `docs/<folder>.md` and deletes `docs/<folder>/`. Takes the folder name as a parameter (injected by the tool). | Piped to `claude -p` as the initial message |
| `bootstrap-detect.md` | One-shot prompt for inspecting a repo and proposing bootstrap commands for fresh worktrees. Used by §6.1 when a repo has no `cpe.config.json` and the user opts into LLM-assisted detection. Constrained via `--json-schema` to return a structured suggestion (array of commands, files inspected, reasoning, blockers). | `claude -p --output-format=json --json-schema <bootstrap-schema>`, one-off per repo |

The `next-phase` skill has no embedded equivalent — its logic *is* the tool (read `meta.json` to find the next pending phase, spawn `claude -p` with that phase's prompt file).

**Versioning**: plans already generated by an older version of the tool retain their phase prompts; updates to the embedded `planbot.md` only affect new plans. The embedded `summarise.md` is re-read on every run, so improvements to summarisation apply immediately.

### 4.2 State ownership

The tool's own JSON files (`meta.json` per run, see §5) are the **authoritative source of phase state** — which phase is next, which are complete, retry counts, commit SHAs, timestamps. The tool never parses `PROGRESS.md` to make decisions, because LLM-generated markdown table formatting is too inconsistent to rely on.

`PROGRESS.md` remains in the repo as a human-readable artifact. The embedded `planbot.md` still instructs Claude to update it as each phase completes — that's useful for anyone browsing the repo — but the tool treats it as cosmetic. If `meta.json` and `PROGRESS.md` disagree, `meta.json` wins.

The set of phases for a plan is determined at queue time by enumerating `PHASE_*.prompt.md` files in `docs/<folder>/` on the filesystem (not by reading PROGRESS.md).

### 4.3 Worktree model

Every run executes in its **own `git worktree`**, not in the user's primary clone of the repo. This means:

- Multiple runs against the same repo can coexist on disk, each on its own branch, without waiting for PRs to merge first
- The user's primary checkout is never touched — they can keep working on `main` (or anything else) while runs process
- Failed runs leave a worktree on disk for inspection; clean recovery via `cpe clean`

Worktrees live at `~/.local/state/cpe/worktrees/<run-id>/` and are created from the primary clone via `git worktree add`. The primary clone is identified at `cpe plan` time via `git rev-parse --show-toplevel`.

**Branch naming**: at `cpe plan` time the final plan slug isn't known yet (planbot picks it). The worktree starts on a temporary branch `cpe/planning-<timestamp>`. Once planning completes and a `docs/<folder>/` is produced, the tool renames the branch (`git branch -m`) and the worktree directory (`git worktree move`) to match `feature/<folder>`. If the user bails on planning (no folder produced), the worktree is removed and the temp branch deleted.

## 5. Storage layout

```
~/.config/cpe/
  config.json          # global settings (defaults, VCS hosts, retry counts)

~/.local/state/cpe/
  queue.json           # the active queue
  runs/
    <run-id>/
      meta.json        # authoritative run + phase state (see below)
      logs/
        bootstrap.log  # output from §7.0 bootstrap commands
        phase-01.log   # captured session output
        phase-02.log
        ...
  worktrees/
    <run-id>/          # git worktree for this run (see §4.3)
```

Shape of `meta.json` (illustrative):

```json
{
  "id": "01H...",
  "primary_repo_path": "/home/richard/code/meatbot",
  "worktree_path": "/home/richard/.local/state/cpe/worktrees/01H.../",
  "plan_folder": "001-add-tests",
  "feature_branch": "feature/001-add-tests",
  "target_branch": "main",
  "remote": { "host": "github.com", "owner": "...", "repo": "..." },
  "status": "executing",
  "total_cost_usd": 0.1875,
  "phases": [
    {
      "number": 1,
      "prompt_file": "PHASE_01.prompt.md",
      "status": "complete",
      "retry_count": 0,
      "commit_sha": "abc1234",
      "started_at": "...",
      "completed_at": "...",
      "session_id": "17b556b6-...",
      "cost_usd": 0.0376,
      "tokens": { "input": 4, "output": 95, "cache_read": 33037, "cache_creation": 6854 },
      "summary": "Added unit test for login function",
      "notes_for_next_phase": ""
    },
    { "number": 2, "prompt_file": "PHASE_02.prompt.md", "status": "executing",  "retry_count": 0, "started_at": "..." },
    { "number": 3, "prompt_file": "PHASE_03.prompt.md", "status": "pending" }
  ]
}
```

The per-phase `session_id`, `cost_usd`, `tokens`, `summary`, and `notes_for_next_phase` are pulled from the envelope (§7.3 step 6) on phase completion. `total_cost_usd` at the run level is the rolling sum across completed phases.

`primary_repo_path` is the user's original clone (for grouping/display). `worktree_path` is where execution actually happens.

### 5.1 State taxonomy

`status` on a run or a phase entry uses the single state taxonomy defined in `docs/DESIGN.md` §2.3. Both runs and phases draw from the same enum so the TUI can render either with the same `state.ts` table:

| State | Used on | Meaning |
|---|---|---|
| `queued` | run | Waiting in the queue |
| `executing` | run, phase | Active right now |
| `retrying` | phase | Failed once, on second attempt |
| `paused` | run | User-initiated pause |
| `paused-limit` | run | Waiting on 5h limit window |
| `finalising` | run | Running summarise + creating PR |
| `complete` | run, phase | Done (run = all phases + PR opened) |
| `pr-created` | run | Push + PR done (terminal pre-cleanup) |
| `failed` | run, phase | Phase failed after retries exhausted (and on a run, the failure caused the run to abort) |
| `pending` | phase | Not yet reached |

Glyphs and colours for each state are in `docs/DESIGN.md` §2.3 — the spec doesn't duplicate them.

## 6. CLI surface

| Command | Purpose |
|---|---|
| `cpe plan [details...]` | Launch interactive `claude` in current repo, seeded with the embedded planbot prompt plus the user's plan details. If no details given, prompt the user for them via multiline input first. Watches `docs/` for a new plan folder; on detection, offers to queue it |
| `cpe queue [folder]` | Add a plan to the queue. If no folder given, list folders under `docs/` and let user pick |
| `cpe start` | Start the TUI / queue processor |
| `cpe status` | Print queue status (non-TUI, for scripting) |
| `cpe list` | List runs in queue |
| `cpe remove <run-id>` | Remove a run from the queue |
| `cpe pause` / `cpe resume` | Pause/resume queue processing |
| `cpe clean` | Remove worktrees for completed/merged runs (and their state). Prompts for confirmation per worktree, or `--all` to sweep |
| `cpe bootstrap [--detect\|--stub\|--edit]` | Manage per-repo bootstrap config. Run inside a repo. Defaults to interactive prompt (detect / stub / cancel). `--detect` runs the LLM detector, `--stub` writes an empty template, `--edit` opens `cpe.config.json` in `$EDITOR` |

### 6.1 Per-repo config: `cpe.config.json`

Lives at the **primary repo root** (committed or gitignored, user's choice — see notes). Holds repo-specific settings the tool needs to set up a worktree. Schema (illustrative):

```json
{
  "bootstrap": [
    "pnpm install",
    "composer install --working-dir=apps/web-app"
  ]
}
```

- `bootstrap` is an **array of shell commands** run in order, in the worktree root, before the first phase of every run on this repo (§7.0). The array form makes per-step logging trivial and reads cleanly when the LLM emits it.
- All bootstrap steps run for every worktree creation, regardless of which paths a phase touches. Sub-project–aware bootstrap is deferred until real usage shows it's needed.
- Future fields (target branch override, max-retries override, etc.) can be added without breaking changes.

**First-time-in-a-repo flow**: when `cpe queue` (or `cpe plan`) is invoked and no `cpe.config.json` exists in the primary repo, the user is prompted:

> *I don't see a `cpe.config.json` for this repo. How would you like to set up the bootstrap command for fresh worktrees?*
>
> *1. Detect with Claude (one-off LLM call, ~$0.05)*
> *2. Create a stub I'll fill in myself*
> *3. Skip — I don't need a bootstrap step*

- **Option 1 (Detect)**: tool spawns a single `claude -p --output-format=json --json-schema <bootstrap-schema>` call with the embedded `bootstrap-detect.md` prompt (§4.1). The prompt instructs Claude to inspect the repo's docs (`README.md`, `CLAUDE.md`, `AGENTS.md`, `QUICK_START.md`, `CONTRIBUTING.md`), manifests at the root and one level deep, and any `Makefile`, then propose bootstrap commands. Response schema:
  ```json
  {
    "type": "object",
    "required": ["commands", "inspected_files", "reasoning"],
    "properties": {
      "commands":        { "type": "array", "items": { "type": "string" } },
      "inspected_files": { "type": "array", "items": { "type": "string" } },
      "reasoning":       { "type": "string", "description": "Per-command rationale" },
      "blockers":        { "type": "array", "items": { "type": "string" }, "description": "Things that couldn't be determined automatically — e.g. .env file requirements" }
    }
  }
  ```
  Tool shows the suggestion (commands, files inspected, reasoning, any blockers) and asks **Y/edit/n**. On Y → save. On edit → open in `$EDITOR` pre-populated. On n → fall through to option 2.

- **Option 2 (Stub)**: writes a commented template with an empty `bootstrap: []` array and inline guidance. Opens it in `$EDITOR` if available.

- **Option 3 (Skip)**: writes `{"bootstrap": []}` so the tool doesn't re-prompt next time. User can `cpe bootstrap --detect` later if they change their mind.

**Should `cpe.config.json` be committed?** User's choice. If committed, the team shares the bootstrap definition; if gitignored, each developer can override. The tool itself is agnostic — it doesn't add or remove a `.gitignore` entry. The stub template includes a comment noting the trade-off.

## 7. Workflow detail

### 7.0 Worktree creation & bootstrap

Runs at the start of every `cpe plan` and every `cpe queue` (for manually-authored plans). Steps:

1. Identify primary repo via `git rev-parse --show-toplevel`
2. **Check for `cpe.config.json`** at the primary repo root. If absent, run the §6.1 first-time prompt before proceeding
3. Create the worktree: `git worktree add ~/.local/state/cpe/worktrees/<run-id> -b <branch> <target-branch>` (branch name is `cpe/planning-<ts>` for `cpe plan`, or `feature/<folder>` for `cpe queue`)
4. **Run bootstrap commands** in order in the worktree root, streaming output to the TUI / a `bootstrap.log`. If any command exits non-zero:
   - For `cpe plan`: abort, tear down the worktree, surface the error
   - For `cpe queue`: mark the run `failed` before any phase runs, log the bootstrap output, move on to the next queued run
5. Proceed to the caller's next step (planbot kickoff in §7.1, or first phase in §7.3)

### 7.1 Plan creation (`cpe plan [details...]`)

1. User runs `cpe plan <details>` inside a repo — e.g. `cpe plan add tests for the user service`
2. If no details were supplied on the command line, CLI opens a multiline input (terminate with EOF / `Ctrl+D`) and captures them
3. **Run §7.0 worktree creation & bootstrap** with branch `cpe/planning-<ts>`. This handles primary-repo identification, config check (prompting for bootstrap setup if first time), worktree add, and running the bootstrap commands. By the end of this step the worktree exists and is buildable.
4. CLI assembles the kickoff message: the embedded `planbot.md` prompt, followed by a separator, followed by the user's plan details (treated as the initial feature request)
5. CLI writes the assembled message to a temp file and spawns Claude as: `claude < temp_file` with `cwd` set to the worktree. **Verified mechanism (probe-claude-cli, 2026-05-17)**: this causes Claude to read the file as the initial user message, generate its first response, and then hand the TUI to the user for follow-up. `--append-system-prompt` and `--system-prompt` only load context — they don't auto-execute the message, which is why stdin redirection is the right tool here.
6. User completes the planning conversation interactively, then exits Claude
7. On Claude exit, CLI checks the worktree's `docs/` for a newly-created folder containing `PROGRESS.md`:
   - **None found** → user bailed: `git worktree remove --force <path>` followed by `git branch -D cpe/planning-<ts>` (the `worktree remove` does not delete the branch — verified by probe-git-worktree.sh). No run recorded.
   - **Found** → rename the branch (`git branch -m cpe/planning-<ts> feature/<folder>`), move the worktree directory to match (`git worktree move <new-path>`), and prompt: "Queue this plan now? [Y/n]"
8. If queued → invoke queue logic. The planning docs are committed as the first commit on the feature branch (`docs: plan <folder>`)

### 7.2 Queueing (`cpe queue`)

When called from `cpe plan`, the worktree, feature branch, and docs commit already exist (§7.1). When called standalone (`cpe queue [folder]`, e.g. on a plan you've authored manually), the tool first runs §7.0 to create the worktree and bootstrap it, then commits the existing `docs/<folder>/` content onto the new feature branch as the first commit.

Pre-checks:
- `PROGRESS.md` exists in the plan folder (presence-checked only, not parsed)
- At least one `PHASE_*.prompt.md` file exists
- Worktree path is available (no collision)

Enumerate phases by globbing `PHASE_*.prompt.md` in the worktree's plan folder, sorted numerically, and write one entry per file into `meta.json.phases` with status `pending`. This is the only point at which the filesystem is the source of truth for the phase list; from here on, `meta.json` is.

Record in `meta.json`:
- Run-id, primary repo path, worktree path
- Plan folder name, feature branch, target branch
- Detected remote (GitHub/Gitea/other)
- Phase list (as above)

### 7.3 Phase execution (per phase, per run)

The next phase to run is determined by scanning `meta.json.phases` for the first entry with status `pending` (or `executing` if resuming after a crash). PROGRESS.md is not consulted.

1. **Limit check** — if rate-limited, set run to `paused-limit`, poll until window resets
2. **Update state** — set the phase entry status to `executing`, write `meta.json`
3. **Capture HEAD** — `git rev-parse HEAD`, stored on the phase entry
4. **Pre-allocate a session UUID** for this phase invocation. The runner generates a UUID and writes it onto the phase entry in `meta.json` *before* spawning Claude, so the corresponding jsonl file path is known in advance (see §7.3.3)
5. **Spawn session** — `claude -p --session-id <uuid> --output-format=json --json-schema <phase-result-schema> < PHASE_NN.prompt.md` with **`cwd` = `worktree_path`**, stream stdout to TUI pane and `phase-NN.log`. **`--output-format=json` and `--json-schema` are mandatory together**: probe-claude-json-schema (2026-05-17) confirmed `--json-schema` alone with the default text output silently suppresses the structured output. The runner errors out at startup if asked to run without both. Output is a single JSON envelope on stdout when the session ends — for live in-flight observability the runner tails the session's jsonl file (§7.3.3)
6. **Wait for exit**
7. **Parse the JSON envelope** from stdout. Key fields read by the runner:
   - `is_error` (bool) — primary success/failure signal
   - `api_error_status` (int|null) — HTTP status if `is_error`. `429` ⇒ rate-limit hit, treat as §8 limit case (no retry consumed)
   - `terminal_reason` (str) — e.g. `"completed"` for clean exit
   - `stop_reason` (str) — Claude's reason for ending the conversation
   - `structured_output` (object) — the schema-validated phase result (§7.3.1)
   - `usage.{input_tokens, output_tokens, ...}` — store on the phase entry for metrics
   - `total_cost_usd` (float) — store on the phase entry for cost accounting
   - `session_id` (str) — should match the pre-allocated UUID from step 4; sanity-check
   - `permission_denials` (array) — log if non-empty; useful diagnostic when a phase mysteriously fails
8. **Decide phase outcome** using the envelope:
   - `is_error: true, api_error_status: 429` → §8 limit case (pause run, capture `session_id` on the phase entry, don't count retry). On resume, decide between fresh restart and `--resume` per §7.3.2
   - `is_error: true` (other) → phase failure, retry/fail per usual rules
   - `is_error: false` and `structured_output.completed: true` and `structured_output.committed: true` → continue to step 9
   - Anything else (envelope unparseable, missing required schema fields, contradictions) → phase failure
9. **Cross-check HEAD** — `git rev-parse HEAD`:
   - If `structured_output.committed: true` AND HEAD changed → success. Record new HEAD as `commit_sha` in `meta.json`
   - If `structured_output.committed: true` but HEAD is unchanged → failure (Claude misreported), log the discrepancy
10. **Mark complete in `meta.json`** — set `completed_at`, status `complete`, store `summary`, `notes_for_next_phase`, `cost_usd`, `tokens` from the envelope. PROGRESS.md updates by Claude remain cosmetic — see §4.2
11. **Failure handling**:
    - Retry up to `max_retries` (default 1, configurable per-run and globally), incrementing `retry_count`
    - On retry exhaustion: mark phase `failed`, mark run `failed`, move to next queued run
    - Limit-hit (429) does **not** count toward retries — it triggers the §8 wait

### 7.3.1 Phase result schema

Passed to every phase invocation via `--json-schema`. The validated object appears as the `structured_output` key of the response envelope (§7.3 step 6), **not** the top-level `result` field (`result` is for unstructured prose, which is empty when a schema is in use). Embedded in the binary alongside the prompts (§4.1).

```json
{
  "type": "object",
  "required": ["completed", "committed", "summary"],
  "properties": {
    "completed": {
      "type": "boolean",
      "description": "True if the phase's stated goal was fully achieved. False if any part was skipped, deferred, or blocked."
    },
    "committed": {
      "type": "boolean",
      "description": "True if a git commit was made as part of this phase."
    },
    "commit_message": {
      "type": ["string", "null"],
      "description": "The commit message used, or null if no commit was made."
    },
    "summary": {
      "type": "string",
      "description": "One-to-two sentence human-readable description of what changed.",
      "maxLength": 500
    },
    "blockers": {
      "type": "array",
      "items": { "type": "string" },
      "description": "Anything that prevented full completion. Empty if completed cleanly."
    },
    "notes_for_next_phase": {
      "type": "string",
      "description": "Information the next phase should be aware of. Empty if not applicable."
    }
  }
}
```

The embedded `planbot.md` (§4.1) must instruct generated phase prompts to end with: *"Your final message in this conversation must be a JSON object matching the schema you've been given. Do all your work using tools first, then emit only the JSON as your closing message."*

### 7.3.2 Rate-limit recovery: fresh restart vs. resume

When a phase is interrupted by a rate limit (`is_error: true, api_error_status: 429`), the run is paused until the window reopens. The behaviour on resume depends on whether any work had begun:

- **No work done** (limit hit on the first API call): `usage.input_tokens == 0 && total_cost_usd == 0`. Discard the failed `session_id` and **start the phase from scratch** with a fresh `claude -p` call when the window reopens. This is the common case — the runner only kicks off a phase after a successful pre-flight check.
- **Work in progress** (limit hit mid-phase): `usage.input_tokens > 0` or `total_cost_usd > 0`. **Resume the captured session** via `claude --resume <session_id> -p --output-format=json --json-schema <schema>` with a continuation prompt: *"You were interrupted by a rate limit. Continue from where you left off. Some tool calls may have completed partially — verify the state of the working tree before re-running anything. When done, emit your final JSON per the schema."*

The `session_id` from the failed envelope is captured on the phase entry in `meta.json` precisely so a resume is possible after restart.

There's a residual risk: if a tool call was in-flight at the moment the limit hit, Claude may not know whether it landed. The embedded `planbot.md` (§4.1) therefore instructs generated phase prompts to be **idempotency-aware** — check the working tree state before performing each significant action, rather than blindly assuming a clean start. This makes resumed sessions safer.

### 7.3.3 Real-time session observability

The phase envelope only arrives when the session ends, but the TUI's activity feed (`docs/DESIGN.md` §3) needs **live** visibility into what Claude is doing — tool calls, edits, commits — as they happen.

The mechanism:

1. The runner pre-generates a session UUID and passes it via `--session-id <uuid>` (§7.3 step 4)
2. The path to the session's jsonl is therefore known in advance:
   ```
   ~/.claude/projects/<encoded-cwd>/<uuid>.jsonl
   ```
   where `<encoded-cwd>` is the worktree path with `/` replaced by `-` (verified format from probe-claude-data, 2026-05-17)
3. After spawning Claude, the runner tails this file (`fs.watch` + line-buffered read) and parses each new line as JSON
4. Each line is classified into an activity feed event matching the kinds in `docs/DESIGN.md` §3:
   - `message.content[].type === "tool_use"` with `name === "Edit"|"Write"` → `edit` event
   - `message.content[].type === "tool_use"` with `name === "Bash"` → `bash` event
   - `toolUseResult` arriving → completion of the corresponding event (success/failure, duration)
   - Phase start/end and commit events are emitted by the runner itself, not from jsonl
5. Events are pushed onto an in-memory ring buffer the TUI subscribes to. Buffer is TUI-lifetime; not persisted (DESIGN.md §3 "Feed is in-memory only")

The tail also serves the jsonl confirmation pass in §8.3 — same file, same parsing, different consumer.

### 7.4 Finalisation (after final phase)

All commands below run inside the worktree.

1. Spawn headless `claude -p` with the embedded `summarise.md` prompt (folder name injected)
2. Verify `docs/<folder>.md` was created and `docs/<folder>/` was deleted
3. CLI commits the summary (single commit, message: `docs: summarise <folder>`)
4. Push feature branch to remote (`git push -u origin <feature_branch>`)
5. Detect remote host:
   - `github.com` → `gh pr create --base <target> --fill`
   - Self-hosted Gitea (detected via remote URL match against configured Gitea host) → `tea pr create` or REST API
6. Capture PR URL, mark run `complete`, surface URL in TUI
7. **Worktree is retained** for inspection. It will be removed on next `cpe clean` (or auto-cleaned in a future iteration once we can poll the PR for merged status)

## 8. Limit detection

Three signals available, in order of preference. Since the phase runner uses `claude -p --output-format=json --json-schema ...` (§7.3 step 4), the envelope is the natural primary signal.

### 8.1 Envelope-based (primary)

Verified by probe-claude-json-schema (2026-05-17, captured during an active limit). The envelope on a rate-limit hit:

```json
{
  "is_error": true,
  "api_error_status": 429,
  "result": "You've hit your limit · resets 4pm (Europe/London)",
  "stop_reason": "stop_sequence",
  "session_id": "45b28556-...",
  "total_cost_usd": 0,
  "usage": { "input_tokens": 0, "output_tokens": 0, ... },
  "terminal_reason": "completed"
}
```
Exit code: `1`. Duration: ~600ms (no API work attempted).

Logic:
- `is_error: true` AND `api_error_status: 429` → rate-limit hit. Capture `session_id` on the phase entry. Parse reset string from `result` field. Use the §8.2 reset-time parsing algorithm.
- `is_error: true` AND `api_error_status: 500/502/503` → transient API error, retry quickly (separate from session-limit pause)
- `is_error: true` AND `api_error_status: 400/401/403` → genuine error, fail the phase, don't pause
- `is_error: false` → success path

`stop_reason: "stop_sequence"` (vs `"end_turn"` for a clean finish) is also a useful distinguishing marker.

### 8.2 Stdout pattern & reset-time parsing

Two roles:
1. **Fallback** for any `claude -p` invocation that is *not* using `--output-format=json` (e.g. the embedded planbot kickoff in §7.1, which is interactive)
2. **Reset-time parser**, used by both §8.1 and the fallback path — same string format appears in either the envelope's `result` field or the bare-stdout output

Bare-stdout signal, captured from probe-active-limit (2026-05-17) using `claude -p` without `--output-format=json`:

- **Exit code**: `1`
- **stdout** (single line): `You've hit your limit · resets <reset_time>`
- **stderr**: empty
- Returns in ~1s

Anchor regex on the distinctive middle-dot separator `·` (U+00B7) and the literal "resets":

```regex
^You've hit your limit · resets (?P<reset>.+?)$
```

The capture group is a human-readable reset time like `4pm (Europe/London)` — a time-of-day in 12-hour format followed by an IANA timezone name in parentheses. **No date** is included.

**Reset-time parsing algorithm** (used by §8.1 envelope path and §8.2 stdout path):
1. Split the captured string into the time portion and the parenthesised timezone
2. Parse the time as `%-I%p` (e.g. `4pm` → hour 16)
3. Get `now` in the named timezone
4. Build `reset_dt` = today at `reset_hour`, in the named timezone
5. If `reset_dt <= now` (already passed today), add 24 hours
6. `wait_until = reset_dt`

If the regex matches the limit line but the reset string fails to parse, fall back to polling every 5 minutes.

### 8.3 jsonl confirmation (auxiliary)

When a rate-limit error occurs during a session, three fields appear on the relevant message entry in `~/.claude/projects/<encoded-cwd>/<uuid>.jsonl`:

```
error: str           // observed: 10 chars, likely "rate_limit"
isApiErrorMessage: bool
apiErrorStatus: int  // HTTP status code (e.g. 429)
```

Uses:
- **Confirmation**: after marking a run `paused-limit`, scan recent jsonl entries across all projects for `isApiErrorMessage: true` with a timestamp inside the suspected window. Useful as a sanity check
- **Per-account token accounting (v2)**: sum `.message.usage.{input_tokens, output_tokens}` across all jsonl files within the current 5-hour window for predictive "% of window used" display. Aggregate across **all** projects, not just the current run — the limit is per account

### 8.4 Working order during build

1. Implement envelope-based detection (§8.1) — phase runner already needs the envelope for §7.3 anyway. Captures `session_id` for the resume mechanism in §7.3.2
2. Implement reset-time parser (§8.2) as a shared helper used by both paths
3. Implement §8.2 stdout regex for the §7.1 planbot kickoff path (which doesn't use `--output-format=json`)
4. Optional v2: jsonl-driven predictive display in the TUI (§8.3 second use)

## 10. Resilience

- **Tool crash / forced exit mid-phase**: on next `cpe start`, detect run with `executing` status; ask user: resume phase, mark failed, or skip
- **Graceful exit warning**: if `q` pressed while a session is active, confirm before killing (TUI's kill-confirmation modal — DESIGN.md §5.5)
- **Phase-prompt commit failure**: HEAD-unchanged check catches Claude forgetting to commit; counts as a phase failure → retry/fail per usual rules
- **Disk persistence**: queue and run state written after every state change, not just on shutdown
- **State emission**: every transition (queued → executing, executing → complete, etc.) is emitted on an internal event bus the TUI subscribes to. Same bus carries activity feed events from §7.3.3
- **Worktree reconciliation**: on startup, cross-reference `git worktree list` for each primary repo against `meta.json` records; warn on mismatches (worktree deleted out-of-band, or recorded worktree no longer exists)

### 11.1 Claude Code features deliberately not used

Surfaced during probes; documented here so we don't revisit:

- **`claude --worktree` / `-w`**: creates a worktree *per session*, not what we want — our worktrees span many sessions across the whole plan
- **`claude --tmux`**: creates a tmux session; not appropriate inside our own TUI
- **`claude --continue`**: by design, each phase is a *fresh* session for context-drift reasons. (`--session-id` and `--resume` *are* used — see notes below)
- **`claude --from-pr`**: unrelated to our workflow
- **`claude --bare`**: would skip the user's CLAUDE.md / skills / hooks. Keeping these in play preserves the value of a per-repo skills library, even though it slightly reduces phase determinism
- **`claude --max-budget-usd`**: irrelevant on fixed Claude subscriptions, which is the tool's primary target audience
- **`claude --include-partial-messages` / `stream-json` output**: not needed — live observability is achieved by tailing the session's jsonl file (§7.3.3), which is more robust than parsing streaming output and serves multiple consumers

Used selectively:
- **`claude --session-id <uuid>`**: pre-allocated per phase so the runner knows the jsonl path in advance (§7.3 step 4, §7.3.3)
- **`claude --resume <session_id>`**: used only for rate-limit mid-phase recovery when work had begun (§7.3.2)
